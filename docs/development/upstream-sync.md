# Synchronizing Convenient BOJ Workspace

The comparison recorded for P5 runs from upstream v1.3.3 through v1.4.0. The latter is already a parent-side ancestor of the P4.2 workspace. Git ancestry alone does not show which upstream features survived conflict resolution. Keep a behavior inventory alongside the last reviewed upstream SHA. [Upstream at the last review](https://github.com/gaudium1257/Convenient_BOJ/tree/cfb8499d7947fc2f790adaa0bf2aaa0a6ca6a440) · [P5 inventory and verification](P5.md)

1. Read the current phase request, project specification, roadmap and last integration report. Check the worktree, index, branch tips, fork URL and authorized targets. Keep unrelated edits out of the integration. Record both fork tips before making changes.
2. Read upstream with `git ls-remote --symref upstream HEAD refs/heads/main` and `git fetch --no-tags upstream main`. Record the full SHA. Inspect `git log --oneline <previous-upstream>..<new-upstream>`, the changed paths and `git diff <previous-upstream> <new-upstream>`. Inspect the tree for license and third-party notice changes. The original author permitted this fork. The inspected upstream tree has no root license.
3. Compare each feature against the derivative's normal entry points. Follow the popup setting into storage and the content script, editor, service worker, native host, installer and backup as applicable. Record reuse, adaptations and deliberate differences. Preserve upstream attribution and existing data keys. Retain the fixed extension key, host name, validated protocol boundaries, editor worker and manual official submission flow.
4. Integrate in an isolated local commit. Rebuild with the pinned lockfiles when bundled sources change. Exercise the existing regression configurations and add coverage for changed behavior. Verify both positive and unavailable-tool cases with installed Windows Chrome and real compilers. Use disposable profiles, private native registration and local BOJ fixtures. Keep source and test inputs within the machine during verification.
5. Upgrade the last upstream and fork packages in the same disposable Chrome profile. Verify both the active worker and a restored editor. Run `python tools/package.py --ref <verified-commit> --output dist` and `node tests/p0/p5-packages.mjs dist`. Compare ZIP hashes across Windows and CI Git line-ending settings. Inspect third-party notices, manifest paths and extension identity. Record screenshots, failure corrections, unavailable checks, exact commands and commit IDs in the phase report.
6. At an authorized integration gate, fetch the fork again, check ancestry against **both** remote tips, and review intervening work. For a joint update use explicit full branch refspecs and an atomic, ordinary fast-forward push to the owner's fork. Check both published hashes with `git ls-remote`. The upstream and legacy remotes are read-only. Tags, releases, Store uploads and upstream pull requests are outside this procedure.
